# ComfyUI 监听排障与边界（按需分册）

## 地址规范化与代理（细节）

`norm_url()`（与公共层 `comfy_client.norm_url` 同规则）：反斜杠→正斜杠、压重复斜杠、去尾斜杠、去两边空白。
基址末尾带斜杠再拼端点会变成 `//`，网关把 `//` 当成路径的一部分而不是根，表现为接口偶发 404 / 空响应。

⚠️ 本机所有 HTTP 请求走免代理 opener（`_OPENER = build_opener(ProxyHandler({}))`）：裸 `urllib.request.urlopen` 会把请求绕进系统代理，表现为 **502 Bad Gateway / 超时**。
猴补丁替换 `urllib.request.urlopen` 会污染同进程内 `comfy_client` 的其它代理下载，请求统一交给模块内 `_OPENER`。

## 库用法（别的脚本要嵌等待逻辑时）

`fxai-workflow/comfy_client.py` 的 `run_workflow` / `submit_workflow` 已内置本技能：提交前 `Listener(url)` 拿 clientId 写进 `/prompt` 的 body，再 `Listener.wait(pid)` 等结果；排队等 GPU 时用 `GET /queue` 判断还在不在队列。别的脚本照这个模式嵌：

```python
import importlib.util, os
spec = importlib.util.spec_from_file_location(
    "fxai_comfy_watch",
    os.path.join(os.path.dirname(os.path.dirname(SKILL_DIR)), "fxai-comfyui-watcher",
                 "scripts", "comfy_watch.py"))
W = importlib.util.module_from_spec(spec); spec.loader.exec_module(W)

lis = W.Listener("")   # 传本次任务实际用的地址；留空则自动解析
# ... 用 lis.cid 作为 /prompt 的 client_id 提交，拿到 prompt_id ...
task = lis.wait(prompt_id, timeout=3600, tag="mv")   # 返回终态字典，None=交回轮询
lis.close()
```

## 台账文件字段（运行时目录 `~/.workbuddy/runtime/comfy_ws`，可用 `COMFY_WATCH_HOME` 改）

| 文件 | 内容 |
|------|------|
| `state.json` | 全局任务快照：状态、第几镜/采样百分比、最近消息、产物文件名、merged 成片名 |
| `events.jsonl` | 全量事件流，一行一事件，带 prompt_id |
| `tasks/<prompt_id>.log` | 单任务人类可读进度（每条广播一行） |
| `watcher.pid` / `watcher.log` | 常驻进程 pid / 连接与心跳日志 |

任务记录保留最近 200 条，旧的自动清掉。

## 事件通道字段全表

| 事件 | data 字段 | 含义 |
|------|-----------|------|
| `fxai:progress` `scene_executing` | `current,total,duration,frames,message` | 开始渲染第 N/M 个场景 |
| `fxai:progress` `scene_saved` | `scene_index,scene_count,path,message` | 第 N 个场景已生成 |
| `fxai:progress` `upscale_start/done` | 任意 | 超分开始/结束 |
| `fxai:task_saved` | `prompt_id,url,time` | 任务完成，url 形如 `video/merged\|xxx.mp4`、`image/shortdrama_xjz\|016.png` |

通用事件同样解析（兜底 + 节点计数）。

## 终态判据全表

| 信号 | 含义 | 角色 |
|------|------|------|
| `fxai:task_saved` | 有文件被保存（一次工作流来很多条：音频 / 图片 / 每个分镜视频 / 合并片） | 过程事件，只记账不算完成 |
| `execution_success` | 工作流跑完，所有保存动作已结束 | ✅ 终态（自己提交任务时收得到） |
| 静默 `settle` 秒（默认 30） | 最后一次保存之后无新动静 | ✅ 终态兜底（监听别人提交的任务时走这条） |
| `execution_error` / `execution_interrupted` | 报错 / 被中断 | ✅ 终态（失败向） |

**最终产物按任务类型取**（`final_artifact()`）：

| 任务类型 | 最终产物 |
|---|---|
| 视频类（短剧 / MV，有合并环节） | 成片 = `video/merged\|xxx.mp4` |
| 单视频（无合并） | 视频 = 该次保存的 mp4 |
| 纯音频（人声分离等） | 音频 = 该次保存的 wav |
| 图片类（生图 / 四视图 / 场景图） | 图片 = 该次保存的 png |

`next` 与 `wait` 的差别：`wait` 另有「问结果表」的兜底（覆盖连上之前就完成的情况）。

## 三种看进度的方式（细节）

| 方式 | 入口 | 适合 |
|------|------|------|
| 浏览器面板（推荐） | 双击 `progress.html` | 浏览器直连 ComfyUI 的 WebSocket 收广播，零后端、不写文件、不经过对话；显示第 N/M 镜、已保存各类文件、最终产物、完成横幅，可开桌面通知，换服务器在面板顶部改地址 |
| Agent 播报 | `next <pid>` | 让 Agent 在完成那一刻说一句 |
| 过程留档 | `next/wait <pid> --log` | 事后查（`status`/`top`）时才落盘 |

另有 ComfyUI 自己的界面与控制台日志（`http://127.0.0.1:8188`，日志在服务端 ComfyUI 的 `user/comfyui_<端口>.log`，toolkit 在其中打「正在执行第 3/10 个场景，本场景 8.0 秒」），这两处同样不经过对话。

## 台账并发（多个监听同时跑时）


`state.json` 的写入已做并发处理，多进程同时刷盘不崩溃：

- 临时文件名带 pid（`state.json.tmp.<pid>`）——否则多个进程抢同一个临时文件会被 Windows 独占锁拒绝；
- `os.replace` 被并发占用时退避重试 5 次，失败只记账不打断等待；
- 写前先并入磁盘上的最新记录，后写就不会覆盖先写。

⚠️ 残留限制：跨进程是「后写覆盖」，极端并发下**别的**进程刚写的最新一行可能被覆盖掉；
但**每个监听自己那条任务的记录不会丢**（它始终在自己内存里），所以等待与播报不受影响。

## 常驻监听的存活规律


- 常驻进程的存活时长不固定：**别把关键流程挂在「常驻进程一定活着」上**。
- 真正会发生的断线是**服务端把连接 RST 掉**（`[WinError 10054] 远程主机强迫关闭了一个现有的连接`，ComfyUI 重启或清理连接时）。脚本已内置**指数退避重连**（1s 起、封顶 30s，每次重连换新 clientId）。
- 规则就一条：**别把关键流程挂在"常驻进程一定活着"上**。
  - 主力用 `wait <pid>`——自带连接、用完即退，断了会明确报错并自动兜底查结果表。
  - 常驻 `watch` 只用于「同时盯多个任务 / 事后翻台账」，它掉了不影响 `wait`（`wait` 自己也会写台账）。
- 跨会话常驻：`scripts/start_watcher.cmd`（双击，无窗口；或放进 Windows 启动文件夹）。

```bat
@echo off
rem 双击启动全局广播监听（无窗口）。停止：运行 comfy_watch.py stop
start "" /min python -u "%~dp0comfy_watch.py" watch
```

## 排障


| 现象 | 原因 / 处理 |
|------|------------|
| `top` 显示「连接 断开」 | ComfyUI 没起或地址解析到了另一台；先 `comfy_watch.py sid` 看它实际连的哪台，或显式 `--url <地址>` |
| 任务跑完了台账里没有记录 | 该任务没触发 fxai 广播（只有 fxai 节点会发）；此时只能读 `/history` |
| `wait` 一直「台账无记录，自连…」 | 正常：台账里没这条，它在自己连 WS 守着；提示「已连接」即工作正常 |
| 提交脚本报 400 `prompt_no_outputs` | 工作流没有输出节点；`prompt_outputs_failed_validation`/`bad_linked_input` 同理，看 `node_errors` |

## ⚠️「等结果超时」分两种，别一律加超时


**第一种：单纯排队**——任务真的在队列里等 GPU。表现：事件流持续有新 `fxai:progress`、
显存占用在涨。处理：**等着就行，超时给足**（视频 7200s、场景图 3600s），别调小也别重投
（重投只会多排一个）。

**第二种：僵尸占卡**——队列里卡着早已完成的旧任务，显存被占死，新任务永远排不进去。
判定：

| 检查 | 僵尸占卡的表现 |
|---|---|
| `top` | 某任务 `running`，但「开始/更新」是**几十小时前** |
| `status <pid>` | 日志里已经有 `完成：…` / `fxai:task_saved`，产物已落盘 → **状态没归位，不是真在跑** |
| `events.jsonl` | 最后一条是 `task_saved`，之后**长时间无新事件** |
| 15 秒内连采 3 次 `/queue` | `running=N pending=M` **完全不变** |
| `system_stats` | 显存被占掉大半（本例单卡已用 8.3/17.1 GB），空闲不够跑 H3 |

**处理：加超时到天荒地老也没用。** 只能清僵尸队列 / 重启 ComfyUI / 换云端 GPU。
判据一句话：**`running` 但事件流早已 `task_saved` 且长时间无新事件 + 显存被占 = 僵尸。**

⚠️ **别拿 `/queue`、`/history` 判定任务是否完成**：本机这两个接口返回简化格式
（`prompt_id` 退化成数字、`history` 里查不到真实 id），会给出「不在 history = 从未执行完」的
误判。**以 watcher 台账 + 事件流 + 显存三者交叉验证为准。**
