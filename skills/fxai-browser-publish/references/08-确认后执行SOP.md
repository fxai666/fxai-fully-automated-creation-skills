# 08 · 确认后执行 SOP

> **何时读**：发布单确认后逐阶段执行、划定授权边界、处理中断与回滚时。
> 换账号 / 换客户端接手时照这一册续跑，不重新推理、不重复出单、不跳过闸门。

## 一、前置

- 已读 `SKILL.md` 与 02 册；`python -B scripts/resolve_hub.py --check` 显示 `source=global_config`、自检通过。
- 三张票分工见 02 册第八节：发布单是审批票据，任务队列是运行台账，项目材料清单与 `发布信息.md` 是项目账本。三者只互相引用，不复制正文。

## 二、授权边界（硬表）

| 类别 | 动作 | 能否自行执行 |
|---|---|---|
| 纯本地只读 | 环境自检、列出站点、账号列表、登录态校验、任务列表、指针自检、不带媒体的 probe | 可以 |
| 纯本地写入 | 账号登记 / 切默认、建任务、取消、重试、不带确认参数的 `run` | 可以（只写本机队列，未外发） |
| 需用户参与 | 扫码登录（把二维码大图交给用户扫） | 用户扫码后才算完成，不代扫、不索取密码 |
| **外发 · 平台留痕** | 带媒体 probe：上传成片、留下未发布草稿 | 必须单独、明确授权 |
| **外发 · 真实发布** | 带确认参数的 `run` | 必须发布单已确认，且预览截图已人工核对 |

确认参数的帮助文案写着「等同已人工确认发布单」，这是代码语义，**不是授权来源**。授权只来自用户对发布单的明确确认；发布单停留在「待确认」时，永远不加确认参数。

## 三、阶段 0 · 接手与状态核对

换账号 / 换客户端后第一次接手，先判断有无在途工作，勿从头重新出单：

```text
python -B scripts/resolve_hub.py --check
cd "<实例目录>"
accounts list / check / 任务列表
读 发布单/ 最新一份的状态字段
```

| 现状 | 动作 |
|---|---|
| 已有「已确认」发布单 + 队列有任务 | 从对应阶段续跑，不重新审批 |
| 发布单「待确认」 | 停在闸门前，把决策项交回用户 |
| 找不到发布单 | 按 05 册重新出一份待确认单 |

## 四、阶段 1 · 把确认写进发布单

用户确认后，在发布单顶部补确认记录并改状态为 `已确认`：

```text
- 状态：已确认
- 确认时间 / 确认人 / 选定方案
- 授权范围：是否允许带媒体 probe 上传留草稿；是否允许真实发布；本次覆盖哪些站点与账号
- 未授权项：逐项列出
```

授权范围必须逐项写清。含糊的「可以发」不等于同意「上传成片并留下未发布草稿」；两件事分开要授权。

## 五、阶段 2 · 打通通道（逐站，不批量）

先按内容类型确定本次要发哪些「站点 × 类型」：`platforms --type <类型>` 列出全部候选，再与发布单核对。
对其中每个组合，按顺序：登录（扫码优先，只有短信验证码的站点用 `login --manual`）→ 校验登录态 →
先跑 `goto <站点> --type <类型>` 复用已记录的发布页地址（见 09 册），只有 `ENTRY_FAIL` 才走只读 probe
导出该类型的投稿页 DOM → 带媒体 probe 导出上传后表单页 DOM。

同一站点的视频页与图文页是两个地址、两套字段，各自单独校准，不共用一次 probe 的结果（见 10 册）。

- 带媒体 probe 会把成片上传到投稿页并留下未发布草稿，绝不点提交；它须在阶段 1 单独授权。
- 用它校准站点条目的 `fields`、`ai_declaration_texts`、`submit_texts`、`success_hints`，方法见 03 册。
- 两阶段投稿页上传前没有标题 / 简介 / 标签，须按 01 册第九节轮询等待表单出现，禁用固定时长休眠。
- 页面改版只改该站自己的 `config/sites/<站点标识>.json`。
- 每站校准完记「已用真实表单页验证 / 未验证」，未验证的站点不进阶段 5。

## 六、阶段 3 · 回填发布单并二次确认

阶段 2 会看到真实页面，把下列四项从「待确认」回填：

| 项 | 回填内容 | 拿不到时 |
|---|---|---|
| AI 声明入口 | 控件文案与勾选方式 | 保留「待确认」，不记成已勾选 |
| 分区 / 分类 | 真实下拉项 | 不新建、不误选 |
| 合集 / 专辑 | 是否真有该选项 | 记「站点无此项」，不硬造 |
| 封面控件 | 有无自定义封面入口、自动截帧规则 | 用项目目录指定帧，不用自动截帧 |

回填后**重新出单给用户过目一次**。真实页面信息与拟稿不一致属新信息，不得沿用旧授权直接发。

## 七、阶段 4 · 生成项目侧材料清单

按 `templates/发布材料清单.md` 在**项目目录**生成 `发布材料清单.md`：成片规格用 `ffprobe` 实测值；成片只读，不重剪、不转码、不改名；封面 / 标题 / 简介 / 标签 / AI 显式标识落项目目录；**逐站记下实际使用的文案档位（13 册）**，便于回执与复盘时核对口径；「关联发布单」指向阶段 1 那份票据，不复制风险表正文；站点与账号从实例目录读，不在清单里硬编码。

## 八、阶段 5 · 建任务

```text
add --platform <站点> --video "<成片绝对路径>" --title "<该站标题>" \
  --desc "<含 AI 显式标识的简介>" --tags "<逗号分隔>" \
  --cover "<封面绝对路径>" --ai --account <账号> --at "<YYYY-MM-DD HH:MM>"
```

- 每条任务带 AI 标记；页面有声明入口就勾选，文案里的显式标识仍须保留。
- 逐站差异化文案，错峰定时，勿同一时刻一字不差群发。
- **建任务前逐站定文案档位**：读实例目录站点条目 `copy_profile`（类型层可覆盖），未标注按 `mass`；按 13 册分写标题与详情，跑一遍 13 册第六节自检清单。`mass` 站标题不得有技术名词、详情不得写怎么做 / 怎么实现 / 制作过程、公共页脚须已关闭；两档都保留 AI 显式标识。过不了自检就改文案重新出单给用户过目，不带疑问建任务。
- 只给「阶段 1 已授权 + 阶段 2 已校准 + 阶段 5 档位自检通过」的站点建任务。此时仍未外发。

## 九、阶段 6 · 按授权模式执行

交付只有两种模式，外加一个调试开关：

| 命令 | 行为 | 平台侧结果 |
|---|---|---|
| `run` | **直接发布**（默认），真无头静默跑 | 作品提交，进审核 |
| `run --draft` | 存草稿 | 内容落进平台草稿箱，不提交 |
| `run --dry` | 只调试 | 只上传填表截图，不点任何按钮 |
| `run --hold N` | 强制按人工处理，最多等 N 秒 | 同上，人完成后自动继续 |
| `run --headed` | 排查时才用：窗口直接开在屏幕内 | 同上 |

默认**真无头**：没有窗口、不抢焦点、任务栏不出现，速度也最快。需要人工时由流程自己切成有头把这一条重跑一次，使用者不用加任何参数。

**闸门落在票据上，不在命令行参数上**：`run` 先读发布单里的 `授权模式：publish` 或 `授权模式：draft` 行——写 `publish` 才直接发，写 `draft` 时自动降级为存草稿，找不到匹配票据直接拒绝执行。这样默认动作就是发布，同时保留人工确认这一层。

首次执行建议先 `--dry` 看一眼截图：标题 / 简介 / 标签是否填对、封面是否为指定帧、AI 声明是否勾上、分区是否选对、有无误触提交。**同时按 13 册核对文案**：`mass` 站标题里有没有混进技术名词、详情里有没有制作过程 / 参数 / 资源链接、公共页脚有没有被关掉、`tech` 站技术名词是不是真排在最前面、两档的 AI 显式标识是否都还在。有问题改实例配置或改任务，勿带着疑问直接发。

平台不会自动留存草稿：`--dry` 关掉浏览器后页面上什么都没留下，要落进草稿箱必须显式点存草稿类按钮，即 `--draft`。

## 九之二、真无头优先，需要人工才自动切成有头重跑

默认**真无头**：没有窗口、不抢焦点、任务栏不出现，跑起来对人完全无感。

真无头的问题是没有界面可给人用。解法分两层，**先重跑再露面**：

| 层 | 做什么 | 为什么 |
|---|---|---|
| 第一层 | 无头跑完整流程；判定需要人工时不空等、也不把任务判死，留一张现场截图后返回 `need_manual` | 绝大多数任务一路跑到底，白等和误判都是浪费 |
| 第二层 | 调用方收到 `need_manual` 后**自动以有头模式重跑这一条**，窗口先开在屏幕外 | 人不必记任何参数；窗口先不出现，免得白弹一次 |
| 第三层 | 重跑时若人工信号再次命中，`reveal_window` 把窗口挪到屏幕中央 + 挂横幅 + 等人 | 界面只在确实要用时才出现在人眼前 |

什么时候需要人工介入，全由流程按页面实况自己判定；使用者只管看结果，命令原样照跑。

| 情形 | 判定方式 | 行为 |
|---|---|---|
| 已判定提交成功 | 成功提示 / 页面已离开发布页 | **直接往下走**，不等任何预算 |
| 页面真的出现了人工校验 | 站点条目 `manual_check` 登记的文本 / 选择器命中 | 无头：返回 `need_manual` 交给上层重跑；有头：挪窗口 + 挂横幅 + 等人 |
| 明确要人全程盯着 | 显式 `--hold` | 同上，停留上限取 `--hold` 的秒数 |

窗口露面时的三条规矩：

| 步 | 做什么 | 为什么 |
|---|---|---|
| 1 | 窗口**挪到屏幕中央并置前**（CDP `Browser.setWindowBounds` 改 left/top，并恢复 `windowState: normal`），留一点边距 | 有头重跑时窗口先开在屏幕外，不挪回来人看不见也点不到；正好顶满屏幕又不方便他同时看别的窗口 |
| 2 | 页面顶部挂一条**红色横幅**，写明「需要你接手：具体做什么」 | 人切过去第一眼就知道要干什么，不用回头翻聊天记录 |
| 3 | 控制台同时打**同一条提示**，并说明等待多久、之后是否自动继续 | 命令行这一侧也留痕，事后可复盘 |

要点：

- 横幅用 `position: fixed` 固定在顶部，`pointer-events: none`——只提示，绝不挡住他要点的按钮。
- 提示文案写到**动作级**：「输入手机收到的短信验证码并点验证」，比「请完成验证」有用得多。
- **等待期间持续探测成功信号**，人一完成就立刻继续，不等满预算；等待秒数是上限，不是必须耗完的时长。
- 已经判定成功的，**直接跳过等待**——不需要人工还占着窗口干等，是纯粹的时间浪费。
- 等待期间**脚本停手**，鼠标交给用户；等待结束后照常走判成功流程。
- 真拿不到窗口句柄时（CDP 不可用），退化为让页面自己 `window.moveTo` 回到左上角，仍然把人能操作放在第一位。
- 重跑一次要重新上传、重新填表，成本是十几秒；因此 `manual_check` 必须**只登记真会出现的信号**，把一次性校验误登记成常驻信号，会让每一条任务都白重跑一遍。

站点条目用 `manual_hint` 写这一站的具体提示语，用 `manual_check` 登记「什么信号才代表这次真的需要人工」，`wait_s` 给等待上限。**首次接入时可能需要人工的站，跑通几次后要回头把 `manual_check` 收紧**，别让一次性校验变成每次都等。

## 十、阶段 7 · 真实发布

按站点逐条放行，优先单站点提交，首发一站观察审核结果，再推其余站点；勿一次全量群发。逐条记录返回的 `status` 与 `result_url`。`published_unverified`（没匹配到成功文案）保留该状态并附结果截图人工核对，不得写成「已发布」。`result_url` 是投稿结果页 URL，不等于公开作品链接。

## 十一、阶段 8 · 回写项目与回查链接

按 06 册：

```text
1. 读任务队列：platform / account / title / status / result_url / preview_path
2. 在项目目录生成或追加 发布信息.md 一行
   - 刚提交：状态「已提交」，链接栏「待补公开链接」，备注记结果截图路径
   - 审核通过拿到公开链接：同一行改成「已发布」并填真实地址
3. fxai_project.py stage "<项目目录>" --publish 2      仅全部确认完成后
4. fxai_project.py memory "<项目目录>" --add "<日期 首发站点与账号>" --tag 决策
5. 更新 发布材料清单.md 状态；发布单改为 已执行
```

绝不手写 `_fxai_project.json`、`交付清单.json`；无分集项目勿用 `deliver` 硬造一集。

## 十二、状态对照表

| 发布单 | 任务队列 | `发布信息.md` | 含义 |
|---|---|---|---|
| 待确认 | 无任务 | 无 | 闸门前，什么都不许外发 |
| 已确认 | `pending` | 无 | 已授权，可建任务 / 预览 |
| 已确认 | `pending`（已写 `preview_path`） | 无 | `--dry` 预览过，未发布 |
| 已执行 | `running` → `published` | 已提交 / 审核中 | 已点投稿，公开链接待补 |
| 已执行 | `published` | 已发布 | 回查到公开作品链接 |
| 已执行 | `published_unverified` | 发布未验证 | 附截图人工核对，不美化 |
| 已执行 | `failed` / `cancelled` | 未发布（记原因） | 本地失败或取消 |

任务队列实际状态只有 `pending / running / failed / cancelled / published / published_unverified`；存草稿 / 调试成功后任务回到 `pending` 并只写 `preview_path`。平台「审核中 / 被拒」由人工回查后写进 `发布信息.md`，代码不自动判定。

## 十三、中断与回滚

- 任一阶段失败即停下，先看按账号分目录的任务日志、失败截图与 DOM，勿盲目重试群发。
- 部分站点已提交时，禁用整批重跑，否则已成功的站点会重复投稿；用按站点放行只补未发那一站。
- 明确失败的单条任务走 `retry`；确认不发的走 `cancel`。
- 已提交状态的任务先人工到平台核一遍有无草稿或已发布，再决定重试；拿不准就停在「发布未验证」。
- 阶段 2 留下的未发布草稿，由用户在平台侧自行清理或明确授权后处理，发布能力不擅自删平台内容。

## 十四、收尾判据

`发布信息.md` 有逐站记录、任务队列无悬空在途任务、发布单为「已执行」、`stages.publish` 已由脚本点亮——四条齐了才算这一轮发布闭环。
