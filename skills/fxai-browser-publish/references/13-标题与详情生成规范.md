# 13 · 标题与详情生成规范（发布执行标准）

> **何时读**：拟标题 / 写简介 / 定标签、出发布单、建任务、`--dry` 预览核对文案时。
> 这是**强制发布标准**，不是写作建议。任何一条发布任务的标题与详情，都要先定档、再落笔、再自检。
> 本册属 L0 公共规范：只定义「怎么写」，**不写任何具体站点名、域名、按钮文案、字数上限**。某站属于哪一档、某档的字数上限是多少，一律落实例目录（L2）站点条目。

## 一、一句话口径

**同一部作品，两类受众，两套文案，不许一份稿子改改群发。**

| 档位 | 面向谁 | 标题 | 详情 |
|---|---|---|---|
| `tech` 技术向 | 搞技术的人 | **技术名词前置**，一眼认出技术点 | 可以讲方案、模型、流程、参数、实现要点、复现方式 |
| `mass` 大众向 | 普通用户 | **娱乐化钩子**，一个技术名词都不写 | 只讲作品本身：画面、人物、情绪、故事、看点；**不写怎么做的、怎么实现的、怎么完成技术流程** |

铁则：

- **默认档位是 `mass`**：站点条目没写 `copy_profile`，一律按大众向写。宁可少写技术，不可多写一个技术名词。
- 两档都必须保留 **AI 生成显式标识**（见第六节），这是合规要求，不是「技术实现描述」。
- 档位不是站点属性，是「**站点 × 内容类型**」这一格的属性：顶层 `copy_profile` 是站点默认，`types.<类型>.copy_profile` 可覆盖。接入单位是格不是站点，见 `SKILL.md`「初始化之后先做这件事」。
- 技能包不保存「哪个站点是哪一档」的对照表，也不在规范里点名任何站点；这张表只存在于实例目录，改版只改实例配置，本册零改动。

## 二、标题规则

### 2.1 `tech` 技术向

1. **技术名词必须放在最前面**——标题的前几个字就是技术点，勿拿场景、情绪、悬念开头把它挤到后面。
2. 结构：`「<技术名词> ＋ <做了什么 / 得到什么结果>」`，例：`「<模型名>全场景替换」`这一路写法。
3. 允许出现：模型 / 工具 / 工作流 / 节点 / 整合包名、能力名（替换、复现、对齐、超分）、规格参数（帧数、fps、分辨率）、「实测」「复盘」这类技术受众熟悉的词。
4. 目标是**让搞技术的人在信息流里一眼认出这是自己关心的东西**，不是让所有人点进来。

### 2.2 `mass` 大众向

1. **开头就是钩子**：反差、悬念、名场面、情绪、第二人称、具体一秒、一句口语。让人想点进来看，而不是让人看懂技术方案。
2. **标题里一个技术名词都不许有**。禁用清单（不限于此，遇到新词按同一原则判）：

   - 模型名、工具名、工作流 / 节点 / 整合包 / 插件名；
   - 「全场景替换」「角色替换」「AI 生成」「AI 制作」「智能合成」这类把**工艺**当看点的说法；
   - 「逐帧」「帧对齐」「帧数」「fps」「分辨率」「编码」「超分」「重绘」「音轨」「配乐生成」这类**参数与制作痕迹**；
   - 「实测」「教程」「复现」「技术方案」「实现」这类把作品写成案例 / 教程的词。

3. 标题写的是**画面里发生的事**，不是**我们做了什么**。写「狮头举起来那一刻，人换成了机甲女主」，不写「用 AI 把舞狮人换成机甲女主」。
4. 站点短标题一律用 `auto:N` 由本条作品标题**自动截取**，不得写死一句短标题——写死必在换作品时忘记改，把上一部标题带进新作品。

### 2.3 两档共同

- 字数上限只在实例目录站点条目里查，本册不写具体数字。
- 不写外链、不冒充他人名义、不虚构事实、不用占位词当真标题。
- 逐站差异化，不把技术站的标题原样搬到大众站，也不把大众站标题改两个词发全网。

## 三、详情规则

### 3.1 `tech` 技术向

可以写：技术方案与选型、模型与流程、替换 / 保留的范围、帧数与时序、分辨率与帧率、素材与音轨处理、复现要点、规格实测值、资料与开源地址、技术话题标签。面向的是「想自己也做一遍的人」。

### 3.2 `mass` 大众向 —— 三写 / 四不写

**只写看得见、感受得到的东西：**

| 写 | 例（抽象写法，不含任何站点信息） |
|---|---|
| 画面里有什么 | 人物、场景、道具、色调、氛围 |
| 情绪与看点 | 飒、反差、燃、好笑、某一秒的高光 |
| 一句钩子 / 互动 | 「你最喜欢哪一帧」「看到最后有反转」 |
| AI 显式标识 | 见第六节，必写 |

**一律不写：**

1. **怎么做 / 怎么实现 / 怎么完成技术流程**：任何把镜头对准幕后、把作品写成案例复盘的叙述。
2. **技术名词与实现细节**：模型、节点、工作流、整合包、脚本、参数、帧数、fps、分辨率、编码、超分、「逐帧保留」「时序对齐」。
3. **制作痕迹**：「烧录字幕已抹除」「原片音轨未使用」「配乐重新生成」「字幕重做」「素材替换范围」——观众不需要知道，写出来就变成技术展示了。
4. **资料下载 / 开源地址 / 网盘链接 / 资源包说明**：这是技术向资源信息，大众向详情里出现就是「不像一个正常作品」。

> **判断口诀**：把详情念给一个不懂技术的朋友听，只要他听出「哦这是教人做片的」，就是写错了；他只听出「哦这片子挺好看」，才是对的。

**参照改写表**（左边一律不许出现在大众向文案里）：

| 技术向表述 | 大众向改写方向 |
|---|---|
| 「AI 角色替换 / 全场景替换」 | 直接写画面里换了谁、变成了什么样，不提工艺 |
| 「534 帧逐帧对齐 / 动作一帧没动」 | 「动作一点没走样」这类口语，或干脆不写 |
| 「720×1280 / 30fps / 17.8s」 | 不写参数；想说长度就写「十几秒」 |
| 「音轨重新生成 / 配乐重新生成」 | 不写；最多写「配乐很上头」 |
| 「工作流 / 节点 / 整合包下载地址」 | 整段删掉，不改写 |

### 3.3 公共文案块按档位收口

实例目录 `公共/公共文案块.json` 的 `descr_footer`（资料下载、开源地址、网盘链接、资源包说明）属**技术向信息**：

- `tech` 档：按 05 册规则正常追加。
- `mass` 档：**不得追加到详情**。由实例层置 `footer_in_desc: false`（保留公共标签）或 `common_block: false`（连公共标签一起关），具体由该站点条目决定。
- 公共标签也要过一遍「无技术名词」检查：若站点把标签并进标题，带工艺 / 自动化意味的公共标签不得进入大众向标题，实例层用站点自定义标签覆盖。
- 改 `公共文案块.json` 是全局动作，勿为单站收口改公共文件；按站点 / 按类型关开关。

## 四、AI 显式标识是例外，必须保留（红线）

《人工智能生成合成内容标识办法》要求的**显式标识**是合规义务，**不属于「技术实现描述」**：

- 详情里那句「本片人物形象与场景由人工智能生成合成」之类的显式标识，`mass` 档**同样必须保留**；
- 画面里的 AI 角标、任务上的 AI 标记、平台声明入口的勾选，两档一律照做；
- **不许拿「不写技术」当理由删掉 AI 声明**。少了标识，不是文案风格问题，是合规缺口，发布单风险栏必须拦下。

显式标识与「怎么做的」的分界：只说明「这是 AI 生成合成内容」，不展开模型、流程、参数、替换手法。

## 五、生成与执行流程（卡在哪个环节）

| 环节 | 必做动作 | 归属册 |
|---|---|---|
| 1 · 定档 | 逐站读实例目录站点条目 `copy_profile`（类型层可覆盖）；没写就按 `mass` | 本册、02 册 |
| 2 · 分写 | 每站各写一份标题 + 详情 + 标签，按档位落笔；**先写大众向，再写技术向**，防止技术稿的措辞串过去 | 本册 |
| 3 · 出单 | 发布单逐站物料里写明该站档位；把档位核对结果写进风险清单 | 05 册、本册 |
| 4 · 确认 | 用户对发布单明确确认前，不上传、不发布、不改项目清单 | 05 册 |
| 5 · 建任务 | `add` 用的就是这个已确认档位下的文案，不在命令行临时改口径 | 08 册阶段 5 |
| 6 · 预览核对 | `--dry` 截图逐站核对：标题有无技术名词、详情有无制作过程、页脚是否被关掉、AI 标识是否还在 | 08 册阶段 6 |
| 7 · 回执 | 项目侧 `发布材料清单.md` / `发布信息.md` 记实际使用档位 | 06 册 |

**新站点接入时必须同时定档**：`config/接入清单.md` 那一格没填 `copy_profile`，按 `mass` 处理，不得默认按技术向写。

## 六、出单前自检清单（逐站过，全过才出单）

- [ ] 该站档位已确定，发布单里已标注；未标注即视为 `mass`。
- [ ] `mass` 站：标题**前若干字**里没有模型 / 工具 / 工艺 / 参数 / 「实测」「教程」类词。
- [ ] `mass` 站：详情里没有「怎么做的 / 怎么实现的 / 怎么完成技术流程」，没有帧数、fps、分辨率、编码、音轨、字幕、配乐重做等制作痕迹。
- [ ] `mass` 站：没有资料下载、开源地址、网盘链接、资源包说明；公共页脚已按档位关闭。
- [ ] 两档：AI 显式标识仍在文案里，AI 角标在画面里，AI 声明入口按平台实际勾选。
- [ ] 两档：标签过了「无技术名词」检查；进标题的标签也过了同一检查。
- [ ] 逐站文案确实不同；短标题是 `auto:N` 而不是写死的一句话。
- [ ] `tech` 站：技术名词确实排在标题最前面，没被场景 / 情绪挤到后面。

任一不过 → **改文案，重新出单给用户过目**，不带疑问建任务。

## 七、违规处理

| 发现时点 | 处理 |
|---|---|
| 出单 / 预览阶段 | 改文案后重新过目；属页面真实信息变化按 08 册阶段 6 二次确认 |
| 已建任务、未提交 | 改任务文案再执行，本地动作，可自行处理 |
| **已发布到平台** | **不擅自改平台稿件**。改稿 / 删稿 / 重发都是外发动作，须用户单独明确授权；先在发布单风险栏与项目 `发布信息.md` 备注里如实记下，等用户决定 |

历史文案不符合本册，不构成「自动批量改稿」的授权；本册自生效起只管**之后**的发布。

## 八、与其他册的边界

- 05 册管**物料有哪些、发布单怎么出**；本册管**标题和详情按什么口径写**，两者配合，不互相替代。
- 07 册管合规；本册第四节的 AI 显式标识是合规红线，优先级高于一切文案风格偏好。
- 08 册管**确认后怎么跑**；本册的定档与自检卡在出单、建任务、`--dry` 三个环节。
- 06 册管**发布后怎么写回执**；本册不重复。
- 具体站点 → 档位映射、字数上限、按钮文案、页脚开关值，全在实例目录（L2），本册零记录。
