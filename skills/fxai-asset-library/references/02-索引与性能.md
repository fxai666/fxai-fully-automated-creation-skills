# 索引与性能

库过千条之后，「每次把台账读进内存逐条算分」就变成瓶颈。这册讲索引怎么搭、为什么这么搭、慢了怎么调。

## 一、为什么不用 SQLite 自带的 FTS5

试过，都不行：

| 方案 | 问题 |
|---|---|
| FTS5 + `unicode61` | 不切中文，一整段 CJK 当一个 token，搜「录屏」命中不了「仙宫云录屏」，除非整句一致 |
| FTS5 + `trigram` | 要求查询 **≥3 字**，而「录屏」「换脸」「对比」全是 2 字，直接失配 |
| 前缀索引 | 中文没有词边界，前缀匹配对「开实例」这种中间词无效 |

所以自建倒排：**CJK 段 = 整串 + 全部二元组（bigram），拉丁/数字 = 整词小写**。
- 「录屏」→ `录屏`
- 「仙宫云镜像广场」→ `仙宫云镜像广场`（整串）+ `仙宫` `宫云` `云镜` `镜像` `像广` `广场`
  于是搜「仙宫云」「镜像」「仙宫云镜像」都能命中这段长文本。

代价是倒排项偏多（20 000 条约 91 万个），换来的是一次性建索引 13 秒、之后查询都是毫秒级。

## 二、表结构

`<库根>/_库/.index/lib.db`（WAL 模式，可随删随建）

| 表 | 内容 |
|---|---|
| `assets` | 每条素材一行：编号、文件、类型、形态、主题、规格、大小、入库、缩略图有无、用途、标签、来源、md5 |
| `terms` | 倒排：`(term, code, w)`，`w` = 该词在这条里命中的**最高字段权重** |
| `refs` | 项目引用：`(code, project, file)`，由扫各项目 `素材登记.json` 的 `库内` 字段得到 |
| `meta` | `fingerprint`（台账 mtime:size）、`built_at`、`build_ms`、`count`、`refs_root` |

索引只在 `meta.fingerprint` 与当前台账不一致时重建，所以「台账没动」的检索是零重建成本的。
`PRAGMA user_version = SCHEMA_VER`：改表结构时把 `idx.py` 里的 `SCHEMA_VER` 加 1，旧库下次连接自动补表补索引。

## 三、字段权重

| 字段 | 权重 | 理由 |
|---|---|---|
| 编号 | 12 | 直接输入编号说明目标明确 |
| 文件 / 原名 | 8 | 名字里通常就是内容摘要 |
| 主题（分类） | 6 | 找素材常按项目/主题起手 |
| 标签 | 6 | 人工埋的检索词 |
| 形态 | 4 | 「录屏」「对比」这类粗筛 |
| 用途 | 3 | 长文本，命中多但区分度低 |
| 规格 | 2 | `1024x960`、`787f` 这类 |
| 来源 | 1 | 溯源用，一般不是检索意图 |

同一个词出现在多个字段，取**最高**权重，不累加 —— 避免「用途里刷十遍」把一条烂素材顶到前面。

## 四、两层检索（关键）

一次查询分两步：

1. **第一层**：只匹配 `w >= 4` 的倒排项（编号/文件名/主题/标签/形态）。
2. **第二层**：若第一层命中数不足 `limit`，再放开到全部倒排项（含用途/来源）。

为什么这么切：用途字段的二元组占了倒排表的大头，把它们排除在第一层外，常见查询的聚合量能少一个数量级；
而真正只写在用途里的内容（「纯色底」「裁画框」）依然能在第二层找到，不会漏。

语义：**词之间 AND，词内部子词 OR**。
`find 仙宫云 开实例` = 必须同时满足「仙宫云」和「开实例」两簇；每簇内部命中任一子词即可。

## 五、慢在哪里，怎么改的

按优化顺序记下来，避免以后重走：

| 做法 | 问题 | 改法 |
|---|---|---|
| 每次 `find` 都 `lib_load()` 解析 3.3MB 台账 | 白花 20~80ms | 先看 `meta.fingerprint`，新鲜就不读台账 |
| 每次连接都跑建表语句 + `journal_mode` | 每次多 3~5ms | 只在 `user_version` 落后时建；`synchronous=NORMAL` 每次设（否则默认 FULL 会 fsync） |
| 边聚合边 `JOIN assets` | 每个倒排命中都回查一次资产行，多关键词爆炸 | 先在 `terms` 里聚合出 `(code, score)`，再按编号一次性回查 |
| `terms` 只有 `(term, code)` 主键 | `DELETE ... WHERE code=?` 全表扫 91 万行，单条改 284ms | 补 `ix_terms_code`，降到 8ms |

## 六、实测（本机 NVMe）

纯检索耗时，不含 Python 进程启动：

| 规模 | 查询 | 索引 | 逐个扫描 | 提速 |
|---|---|---|---|---|
| 5 000 | 录屏 | 1.4 ms | 7.4 ms | 5.3× |
| 5 000 | 录屏 + 仙宫云 | 1.9 ms | 9.3 ms | 4.8× |
| 5 000 | 仙宫云 + 镜像 + 录屏 | 3.0 ms | 11.6 ms | 3.8× |
| 20 000 | 录屏 | 2.1 ms | 29.3 ms | 14.2× |
| 20 000 | 仙宫云 + 镜像 + 录屏 | 5.3 ms | 45.9 ms | 8.7× |
| 20 000 | 引用反查 | 1.7 ms | 115 ms | ~68× |

建索引：5 000 条 2.2 s / 22.9 万倒排项；20 000 条 13.6 s / 91.6 万倒排项。
单条增删改：约 8 ms（走增量，不重建）。
看板：20 000 条生成 0.5 s、HTML 5.9 MB，首屏只渲染 48 张卡。

> 注意：命令行 `find` 的总耗时还含 Python 启动（~70ms），5000 条时两者差别不明显；
> 真正拉开差距的是纯检索部分，以及引用反查这种「需要扫全盘台账」的操作。

## 七、日常维护

| 场景 | 做什么 |
|---|---|
| 刚批量导入一批 | `lib.py reindex` |
| 手改过 `库内清单.json` | 不用管，下次 `find` 自动发现指纹变了会重建 |
| 换了项目目录 / 新项目引用了素材 | `lib.py reindex`（重扫引用表） |
| 检索结果怪、怀疑索引坏 | `rm -rf _库/.index` 后 `lib.py reindex` |
| 看索引多大 | `lib.py stats` |

`.index/` 是纯派生数据，**不进版本库、不做备份**，删了随时重建。

## 八、可以往上加的能力（还没做）

按投入产出排序：

1. **拼音与首字母**（`xjyg` → 仙宫云）—— 在 `row_terms` 里加一路 `pypinyin` 生成的倒排项
2. **同义词/别名表**（`开机器` ≡ `开实例`）—— 建一张 `alias(term, canonical)`，查询前展开
3. **时效加权**（近期用过的往前排）—— `assets` 加 `last_used`，排序时叠加
4. **视觉相似**（找「和这张构图差不多的」）—— 需要向量库，属于另一个量级，暂不做

加之前先问：现在的毫秒级已经够用，别为想象中的规模提前复杂化。
