# 02 · 音色与服务

> **何时读**：登记/换音色、改服务地址、换引擎、改全局配置时。

## 音色库

登记后 `--speaker <id>` 直选。两处合并（全局同名覆盖技能包内的）：

- 全局配置 `~/.workbuddy/fxai_global.json` 的 `tts.speakers`（**女主000 已登记**）
- 技能包内 `speakers.json`（复制 `speakers.example.json` 改）

```json
{ "id": "女主000", "name": "女主000", "ref_audio": "<参考音色路径>",
  "mode": "cross_lingual", "speed": 1.0 }
```

走内置音色（不克隆）的条目：

```json
{ "id": "千问-vivian", "name": "千问薇薇安", "ref_audio": "",
  "qwen_speaker": "vivian", "mode": "cross_lingual", "speed": 1.0 }
```

`ref_audio` 写相对软件数据目录的路径（`voices/xxx.wav`），由 `software_data_dir` 解析；
`--ref-audio` 绝对/相对都认。

## 模式与送参

🔴 **按引擎取模式，不手写**：模式取 `tts.engines.<引擎名>.default_mode`。
CosyVoice3 克隆用 `zero_shot`，千问用 `cross_lingual`。
送 `text`（语气标签 + 正文）、`ref_audio`、`prompt_text`、`mode`。

| 规则 | 说明 |
|---|---|
| 走克隆必给 `prompt_text` | 参考音频的原文；写进音色库条目的 `prompt_text`，或给 `--prompt-text` |
| `prompt_text` 必须与参考音频逐字一致 | 不一致时服务端不报错，但合成内容会被参考音频带偏 |
| 参考音频统一 16kHz 单声道 | 客户端自动转（ffmpeg）；采样率低或缺 `prompt_text` 服务端会报错 |
| `cross_lingual` 仅千问可用 | CosyVoice3 送该模式返回 500 |

## 服务与路由

取值顺序：`--url` > `--engine` 对应引擎的本机地址（本机优先命中）> 该引擎线上地址 > 该引擎本机地址。

引擎名取自 `tts.engines` 的键（`cosyvoice` / `qwen3tts`）；不传 `--engine` 取 `tts.default_engine`。
别名 `qwen` / `cosy` / `cv3` 自动归到正式键名。`--check` 列出全部引擎的本机与线上地址。

```python
tc.engines_list()          # 已登记引擎名
tc.default_engine()        # 默认引擎
tc.local_url(engine)       # 该引擎本机地址
tc.cloud_url(engine)       # 该引擎线上地址
```

| 地址形态 | 服务起不来时 |
|---|---|
| 含 `container.x-gpu.com`（仙宫云） | 自动拉起实例、等就绪；仍不就绪才报错 |
| 本机 / 其他 | 直接报错，由用户自己起本机服务 |

`/health` 带 `model_loaded` 字段的服务：进程活着即视为就绪，`model_loaded=false` 是正常懒加载状态。

```python
tc.status()        # {url, online, model_loaded, sample_rate, idle_timeout, cloud, detail}
tc.is_cloud(url)   # 是否仙宫云容器地址
tc.ensure()        # 保证在线并返回可用地址；云端地址会自动开机
```

## 换引擎：CosyVoice3 ⇄ 千问（Qwen3-TTS）

同一套协议（`POST /synthesize`，字段一致），**切换只改地址**：

| 引擎 | 地址 |
|---|---|
| CosyVoice3 | `http://127.0.0.1:8182` |
| 千问 Qwen3-TTS | `http://127.0.0.1:8086` |

**服务与技能解耦**：服务端独立部署、独立启动；技能只按地址发 HTTP，不拉起、不管理服务（通用法则见 `fxai-standard` 硬规则 6）。

## 并发（2026-10-31 定稿口径）

**默认按显存自动开副本，让多人同时出声。** 一份模型同一时刻只能跑一次推理，
所以「N 个人同时合成」= 显存里放 N 份模型。服务起来时按可用显存自动判定，
`/health` 的 `workers` 就是当前能同时服务的人数。

| 实测（5060Ti 16G，14.8G 可用 → 3 份副本，CosyVoice3 0.5B） | 数值 |
|---|---|
| 单人一段（约 42s 音频） | 22.85s / 25.77s |
| **三人同时提交，各自耗时** | **46.08s / 48.00s / 43.51s** |
| 三人串行排队（对照：第 3 人何时开始） | 66s |
| 并发期间 `/health` 最大延迟 | 24ms |
| 显存占用（3 份） | 12.2G |

- ✅ 三人**同时出声**，各自约为单人耗时的 2 倍（GPU 算力被 3 份平摊）；比排队快得多
  ——排队时第 3 个人要等 66 秒才开始念，现在 43 秒就念完了。
- ✅ 不假死：推理在工作线程里跑，合成期间 `/health` 24ms 回包。
- 🔴 副本不是越多越好：短句小任务（7.5s 级）上多开一份反而更亏（实测 2 份比 1 份慢 25%），
  因为调度开销占比大；长句大任务才划算。够用就行，别贪多。
- 档位：默认 `auto`（`FXAI_CV_WORKERS` 不设 / `0` / `auto`），公式
  `(可用显存 - 1.5G) ÷ 3.6G`，上限 4；`FXAI_CV_WORKERS=N` 或 `--workers N` 强制指定，`1` = 退回严格串行。
- 人手算：每份约 3.6G。16G 卡放 3 份、24G 卡放 4 份（到上限）。同机还跑 ComfyUI 要相应减少——
  自动档位读的是**当前空闲显存**，ComfyUI 占着时会自动少开，不用手调。

### 分段提交怎么落副本（2026-10-31 实测确认）

配音是**顺序分段**提交的：`voice_gen.py` 里 `for` 逐个发 `/synthesize`，一段拿回音频
才发下一段（500 字拆 7 段 = 7 个串行请求）。所以**任何时刻一个任务只占 1 个副本**，
不存在「一个人的七段同时开跑、占满三份显存」。

日志里每条合成带 `[副本N]`，实测（3 份副本）：

| 场景 | 副本分配 | 耗时 |
|---|---|---|
| 单人顺序 4 段 | **全在副本 0** | 12.2 / 5.7 / 6.0 / 5.1 秒（首段含加载） |
| 两人各 3 段并发 | B1 全程副本 0、B2 全程副本 1，交错 0/1/0/1/0/1 | 9~10 秒/段（单人 5~6 秒，GPU 共享变慢） |

- 🔴 **取副本时优先复用「已经在显存里」的那份**（`CosyVoicePool._take_loaded()`）。
  改之前是纯 FIFO 轮转：单人第 1 段用副本 0、第 2 段被轮到副本 1（模型不在显存）→
  现场白等 5~6 秒加载，第 3 段再加载一份 —— 一个人就把三份显存全占了、还多等两次加载，
  和「闲置不占显存」直接冲突。现在单人连续提交始终落在同一份上，只占 3.6G。
- 多人真并发不受影响：热副本正被别人占着（不在空闲队列里），后来的人拿不到才加载新的，
  那时加载是必须的。
- 没人抢副本时**不需要显式粘性**（session_id）：CosyVoice 副本零状态——参考音频 base64
  和 `prompt_text` 每个请求都自带，副本里不存「谁的音色」，所以某段被别的副本接走
  出来还是同一个音色。
- 🔴 各段音色轻微不一致的真因是 **seed**：客户端不传 `seed`、配置也没有 `default_seed` 时，
  服务端每段 `random.randint` → 同一篇稿子的七段各自随机。要稳就给整个任务固定
  `--seed`（`tts_client.synthesize(seed=...)`），跟副本无关。
- 段与段之间没有依赖，理论上可以拿 3 个副本同时合成同一个人 7 段里的 3 段（快 2~3 倍），
  但单人会把池子占满、第二个人直接排队。**当前故意不做**，保持「一人一份」。

### 排队要看得见（2026-10-31 加）

副本全被占时**不是闷头干等**，服务端会先推一条排队事件，客户端立刻能显示
`[tts] 并发已满（2 份副本都在合成），排队中：前方 2 人，最多等 30 秒`。

- 通道：复用已有的 `/ws/progress`，事件 `{"event":"queue","state":"waiting|update",
  "ahead":前方人数,"waiting":排队人数,"workers":副本数,"timeout":排队上限}`。
  拿到副本/超时后推一条 `state=update`（措辞刻意中性——消息是群发的，分不清是谁拿到，
  说「轮到你了」会让别人误以为是叫自己）。
- `ahead` = **正在合成的 + 排在我前面排队的**。只算排队人数会报成 0，
  明明两三个人正占着副本，用户看到「前方 0 人」会以为马上轮到自己。
- 兜底：Python 环境没装 `websockets` 时 WS 静默跳过，客户端会在提交前探一次
  `/health`，`free<=0` 就打印「并发已满，本次提交要排队」。所以提示不依赖 WS 库。

### 排队上限为什么是 30 秒（别随手调大）

🔴 **等待期间 HTTP 响应体一个字节都不发**（FastAPI 要等 handler 返回才发头），
属于「静默连接」。中间任何一层都会把静默连接当死连接掐掉：nginx `proxy_read_timeout`
默认 60s、Cloudflare 100s、负载均衡/浏览器各有阈值。所以：

- 排队上限 `FXAI_CV_BUSY_TIMEOUT=30`（默认）是**安全区**：30 秒到点主动回 503，
  客户端收到的是一个**正常的 HTTP 响应**，连接正常关闭，不存在「断线」。
- 调到分钟级就会开始出现 502/504/连接重置——那不是服务端断的，是中间代理掐的。
- 想让用户等更久，别调大这个值，正确做法只有：
  ① 保持 30s + 客户端 8 秒自动重试（已实现，用户无感）；或
  ② 改走异步任务 `POST /synthesize/async` + 轮询（**已实现**，见下节，客户端默认走这条）。
- 另一个**已经存在的**同源隐患：一次长文本合成本身就可能超过 60 秒。云端若走反向代理，
  必须把读超时调到 300s 以上，否则不是排队被掐，是合成中途被掐。

### 异步排队任务（推荐用法，2026-10-31 加）

排队会超过 30 秒时，走异步通道：**提交立刻拿 task_id，凭 ID 取结果**。全程没有
长连接，排多久都不会断线。

| 步骤 | 接口 | 返回 |
|---|---|---|
| 提交 | `POST /synthesize/async`（body 与 `/synthesize` 完全相同） | `202 {task_id, ahead, queue_len, queue_max}` |
| 查状态 | `GET /task/{id}` | `{state: queued\|running\|done\|error, ahead, waiting_seconds, elapsed, error}` |
| 取结果 | `GET /task/{id}/result` | `{audio_base64, sample_rate, total_duration}`（未完成回 **409**，不是 202） |

- 提交耗时实测 **0.01~0.03 秒**，与合成时长无关。
- 队列有上限 `FXAI_CV_QUEUE_MAX`（默认 50），超了回 503「排队人数过多」。
- 任务结果在内存保留 `FXAI_CV_TASK_TTL`（默认 3600 秒）；**服务重启后旧 task_id 失效**（404）。
- 任务等副本的上限是 `FXAI_CV_TASK_TIMEOUT`（默认 900 秒）—— 因为不涉及连接保活，可以放宽到分钟级。
- 客户端 `tts_client.py` 已默认走这条路：JSON 里没有 `task_id` 或接口 404/405（旧服务端）时，
  自动退回同步 `/synthesize`，两种服务端都能用。

**WebSocket 与 HTTP 的分工（别混）**：

| | 职责 | 断了会怎样 |
|---|---|---|
| HTTP | 提交 / 查状态 / **取音频** | 重试一次即可，结果还在服务端 |
| `/ws/progress` | 只广播进度事件（排队位次、开始、完成） | 少几次实时提示，结果照样拿得到 |

🔴 **不要用 WebSocket 传音频**：几 MB 的 base64 在 WS 里既不好续传，断了就全丢；
广播只负责「到哪一步了」，数据永远走 HTTP。

### 🔴 zero_shot 的参考文本必须与参考音频逐字一致

CosyVoice3 的参考音色克隆走 zero_shot，`prompt_text` **必须就是参考音频里说的话**。
对不上不会报错，只会产出错乱音频：开头多念一段无关的话、时长乱跳、严重时整段无法识别。

实测（同一段 29 字文本、5 个 seed，参考音频实际内容是「希望你以后能够做得比我还好哟」）：

| prompt_text | 5 次时长 | whisper 转写结果 |
|---|---|---|
| ❌ 写成另一句话 | 19.96 / 10.00 / 8.04 / 22.44 / 12.76（极差 14.4s） | 5 个里 4 个开头乱念，1 个整段是噪声 |
| ✅ 与音频一致 | 6.64 / 6.20 / 6.64 / 6.92 / 7.12（极差 0.92s） | 5 个全部正确 |

**排查办法**：拿不准就转写参考音频对一遍 ——
`fxai-whisper-transcribe` 或 `faster_whisper.WhisperModel(<whisper 模型目录>).transcribe(音频)`。

### ⚠️ cross_lingual 在 CosyVoice3 上会报卷积错误

`Calculated padded input size per channel: (3). Kernel size: (4)` —— 参考音频经
speech tokenizer 后长度不足，直接崩。所以 **CosyVoice3 的音色条目 `mode` 必须是
`zero_shot`**，别配 `cross_lingual`（那是千问引擎的用法）。


### 🔴 副本加载必须全池串行（2026-10-31 修，真 500）

三条请求在同一瞬间到达（不是"我念完你再念"，是真正同时），没加载过的副本会
**一起读同一份权重**。实测后果：

- 副本 0 单独加载 8.4s 正常；
- 副本 1、副本 2 同时加载 → 两个都卡过 30s，最后 `收尾等待超时，强制回收` → **HTTP 500**。

修法两处（`apiv3.py`）：
1. `CosyVoiceService(load_lock=...)`，由池子传入**同一把**锁 —— 每个副本各持一把锁等于没锁。
   加载严格串行，一次只读一份盘。
2. `generate_audio` 加 `started` 标志：卡在加载阶段出错时线程根本没起，不该再白等 30s 收尾。

修后同场景：3 条同时提交全部成功，总墙钟 22.4s（含两份首次加载）。

**顺带量到一个关键数字**（用于判断"要不要给 CosyVoice 也做攒批"）：
三份副本全热后，3 条同时 15.4s，3 条串行 20.5s → **并发加速比只有 1.33x**
（千问攒批是 3.1x）。原因是 CosyVoice 单条就已经把 GPU 用得比较满
（LLM + CFM 扩散迭代 + 声码器多阶段都是卷积密集型），没有千问那种
"自回归逐 token、GPU 大量空转"的空档。**所以 CosyVoice 不做攒批**：
理论上限只有 1.33x，却要改进流式逐 token + 变长 padding + CFM 迭代，风险极高。

### 并发满怎么回（503，不是干等）

副本全被占用、且等待超过 `FXAI_CV_BUSY_TIMEOUT`（默认 30s）→ 直接回
`503 资源不足：当前并发已满（N 个人正在合成），请稍后再提交`，并带 `Retry-After` 头。
显存不足以加载新副本时同样回 503：该副本判死退出池（`/health` 的 `alive` 会减少），
剩下的副本继续服务其他人，不会反复 OOM。

客户端 `tts_client.py` 收到这个 503 会先自动等 8 秒重试一次（多半是赶上别人快念完了），
仍失败才把服务端那句提示原样抛出来。

`/health` 字段：`workers`（配置档位）/ `alive`（可用副本，判死会扣）/ `busy`（正在合成的人数）/
`queue`（正在排队等副本的人数）/ `tasks_waiting`（异步任务还有几个没开始）/
`tasks_total`（内存里存着的任务数）/ `free`（还能同时接几个人）/ `busy_timeout`。

两个引擎现状对比：

| | 千问 8086 | CosyVoice 8182 |
|---|---|---|
| HTTP 模型 | `ThreadingHTTPServer`，每请求一线程 | FastAPI，推理丢工作线程 |
| 并发方式 | **攒批**：一份权重，几乎同时到的几条合并成一次 forward | **副本池**：按显存开 N 份模型，各占 3.6G |
| 异步任务 | ✅ `/synthesize/async` + `/task/<id>` + `/task/<id>/result` | ✅ 同左 |
| 排队可见 | ✅ `/health` 的 `queue` / `queue_len` / `batch_stats`、`/task` 的 `ahead` | ✅ 同左 + WS 广播 |
| 满员提示 | 队列超 `FXAI_QWEN_QUEUE_MAX`（64）→ 503 | 副本全占 → 503 资源不足 |
| 合成时 `/health` | 秒回 | 秒回 |
| 显存 | **4.2G 一份，不随人数增长**（KV cache 很小） | 3.6G × 份数 |

**四个服务分别该用什么模式**（2026-10-31 全部实测定案，别再凭感觉换）：

| 服务 | 模型结构 | 采用的方式 | 实测依据 |
|---|---|---|---|
| 千问 TTS 8086 | 1.7B decoder-only 自回归 | **攒批** | 单条 GPU 大量空转；4 条合批 16.2s vs 串行 50.1s（**3.1x**），显存不涨 |
| CosyVoice 8182 | LLM + CFM 扩散迭代 + 声码器 | **副本池**（不做攒批） | 单条已填满 GPU；3 条并发仅 1.33x，攒批上限太低 |
| whisper 8185 | encoder-decoder + VAD | **批量转写 + 多 worker** | VAD 段合批 9.1s vs 21.9s（**2.4x**），汉字数一致 |
| fxai-svc 8187（RVC） | 多个小模型串成 pipeline | **单 worker + 全局锁** | 双进程并发 3.11x 更差、多线程会串音色 |

判断口诀：**单条推理时 GPU 闲着 → 攒批；单条已经吃满 → 只能靠多副本或加卡。**

### 千问的「真并发」= 攒批，不是堆模型（2026-10-31 实测定案）

同一张卡、同一份权重、60 字左右文本，四种做法实测：

| 做法 | 2 条 | 3 条 | 4 条 | 显存 |
|---|---|---|---|---|
| 一条条串行 | 26.4s | ~38s | **50.1s** | 3.92G |
| **batch 一次送进去** | 18.1s | **15.5s** | **16.2s** | **3.98G** |
| 共享权重 + 多线程（各自 forward） | 25.0s | — | — | 3.98G |
| 加载两份模型 + 两线程 | **27.0s**（更慢） | — | — | 7.87G |

- 🔴 **堆模型完全没收益**：两份模型抢同一份算力，27.0s 比共享权重的 25.0s 还差，白多 4.2G。
- 🔴 **多线程共享权重也几乎没收益**：PyTorch 默认 stream 会把 forward 串行化，25.0s ≈ 串行 26.4s。
- ✅ **只有攒批是真的**：4 条 16.2s vs 串行 50.1s（3.1 倍），显存恒定 —— 一份权重、一次前向带多条。
  原因：1.7B 自回归逐 token 解码，单条时 GPU 大部分时间在等 kernel 发射，合批才能填满。

实现：`BatchDispatcher`（`max_batch` 默认 4、攒批窗口 `window` 默认 50ms）。
请求进 `_Job` → 调度线程攒窗口 → 同 `kind`（custom_voice / base）的合成一次 `generate_*` →
按提交顺序 zip 回填各自结果。**单人用只多等 50ms**，多人用凑整批。

隔离性（4 个客户端同时提交不同文本 + 不同音色，whisper 转写核对）：
- 每条转写内容都是自己那份原文，**没有任何一条串成别人的话**；音频时长与各自文本长度严格对应。
- 个别字的差异（「和」听成「或」）来自 TTS 采样随机 + whisper 误听，单独跑同样出现，与合批无关。
- 合批失败不连累别人：`_run()` 捕获整批异常后**退回逐条重跑**，谁的问题谁报错。
- ⚠ `torch.manual_seed` 是全局的：合批时一批只能有一个 seed，指定 seed 的可复现性会打折
  （和 CosyVoice 多副本同样的问题），不影响出声正确性。

实测（两段 56/59 字同时提交）：
```
B1 提交 http=202 耗时0.00s → {'task_id': 'qtts0002', 'state': 'queued', 'ahead': 0}
B2 提交 http=202 耗时0.02s → {'task_id': 'qtts0003', 'state': 'queued', 'ahead': 1}
/health → {'workers': 1, 'busy': 1, 'queue': 1, 'queue_len': 2, 'tasks_waiting': 1}
B1 done 17.5s → 取结果 http=200；B2 随后 done 25.2s → 取结果 http=200
```
未完成时取结果回 **409**（不是错误，客户端继续轮询），任务不存在回 404，
队列超上限回 503。任务结果（含整段音频 base64）保留 `FXAI_QWEN_TASK_TTL`（默认 900s）后自动清理。

### 闲置回收（已验证，2026-10-31）

**每份副本各自计时**，闲置超 `FXAI_CV_IDLE_TIMEOUT`（默认 30s）自动卸载，
**包括服务启动时预加载的那一份**，显存回落到基线：

- 实测：双副本 EAGER 预加载占 **9076 MiB** → 闲置 30s 后 **2051 MiB**（基线），`loaded_count` 2 → 0。
- 卸载后下一次请求**按需只加载用得到的那一份**（不会一次把 N 份都加载）。
- 默认 `FXAI_CV_EAGER=0`：服务起来不占显存，第一次合成才加载（冷盘约 13s、热页缓存约 3s）。
- ⚠️ 批量做配音时建议临时调大（如 `FXAI_CV_IDLE_TIMEOUT=300`），否则段落之间超过 30s 的空档
  会让模型反复重载，每段多花十几秒。
- 正在合成的副本不会被卸（池内 `_busy` 保护）；客户端中途断开时也会先等工作线程收尾再归还。
- 计时在**取用和归还时都刷新**（`slot.touch()`）。否则一次超过阈值的长合成做完，
  `_last_used` 还停在「加载时刻」，副本一还回去就被判闲置当场卸掉，下一个请求又得重载。
  实测（阈值 10s / 合成 16s）：修前会立刻卸载，修后正常保留。

## 全局配置

`~/.workbuddy/fxai_global.json`（路径可用环境变量 `FXAI_GLOBAL_CONFIG` 覆盖）。

### `tts` 段（技能读）

| 字段 | 含义 |
|---|---|
| `default_engine` | 不传 `--engine` 时用的引擎名 |
| `engines` | 按引擎名分节的地址：`{cosyvoice: {local_url, cloud_url}, qwen3tts: {...}}` |
| `local_url` / `cloud_url` | 默认引擎的本机 / 线上地址（旧字段，未配 `engines` 时按它取址） |
| `prefer_local` | 默认 true，本机优先 |
| `default_mode` | 固定 `cross_lingual` |
| `default_speed` | 语速 0.5~2.0 |
| `max_chars_per_chunk` | 长文分句阈值，**最高 80 字**，默认 80（0 = 不分句） |
| `timeout` | 单次合成超时，默认 300s |
| `speakers` | 音色库 |

### `qwen_tts` 段（**服务端**读，技能不读）

| 字段 | 含义 | 默认 |
|---|---|---|
| `port` / `host` | 监听地址 | `8086` / `127.0.0.1` |
| `device` / `dtype` / `attn` | 推理设备与精度 | `auto` / `sdpa` |
| `custom_voice_dir` / `base_dir` | 模型权重目录 | 脚本同级 `models/` 优先，缺失回落 HF 缓存 |
| `hf_cache` | HF 缓存兜底根目录 | 跟随 `HF_HOME` |
| `default_speaker` | 无音色无 speaker 时的内置音色 | `vivian` |
| `max_new_tokens` | 生成长度上限 | `2048` |
| `idle_timeout` | 闲置多久（秒）卸载模型、释放显存；0=常驻不卸。**默认 30，与 CosyVoice3 一致**；环境变量 `FXAI_QWEN3TTS_IDLE_TIMEOUT` 优先级更高 | `30` |
| `reftext_cache` | 已废弃：参考文本改由接口的 `prompt_text` 传，服务端只认这个字段 |
| `log_level` | `quiet` / `normal` / `debug` | `normal` |
